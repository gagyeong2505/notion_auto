# 규칙: pm-workflow

## 적용 범위

- `pm` 서브에이전트와, pm 계획에 따라 에이전트를 호출하는 메인 세션에 적용됩니다.
- 발동 조건: Notion 데이터를 바탕으로 작업물(보고서, 슬라이드, 시트, 메일)을 요청하는 경우. 단순 조회는 pm이 아니라 `notion-db-analyze`로 보냅니다.

## 1. 요청 → 에이전트 매핑

| 요청 표현 (한/영) | 에이전트 | 작업물 |
|---|---|---|
| 보고서, 문서, 회의록, 정리 / report, doc, minutes | `docs-writer` | Google Docs |
| 발표, PPT, 제안서, 슬라이드 / slides, deck, proposal | `slides-writer` | Google Slides |
| 표, 시트, 엑셀, 집계 / sheet, table, tally | `sheets-writer` | Google Sheets |
| 메일, 공유, 안내, 리마인드 / mail, notify, remind | `mail-writer` | Gmail 임시저장 |

- 한 요청에 작업물이 여러 개면 작업물마다 작업을 하나씩 만듭니다.
- 작업물 종류가 불분명하면 추측하지 말고 사용자에게 묻습니다.

## 2. 작업 분할 규칙

- 작업 1개 = 에이전트 1개 + 작업물 1개 + 승인 1회.
- 의존 순서: `sheets` → `docs` → `slides` → `mail` (뒤 작업이 앞 결과를 참조할 수 있으며, 메일은 보통 다른 작업물의 링크를 담습니다).
- 의존 관계가 없는 작업은 "병렬"로 표시합니다.
- 계획당 작업은 최대 5개입니다. 더 필요하면 단계를 나누고 사용자에게 묻습니다.

## 3. 입력 데이터 전달

작성 에이전트에게 넘기는 모든 작업에는 다음을 포함합니다.

- 원본 DB(Personal Tasks / Work / Study)와 사용한 필터 (예: `Due`가 2026-11-23 (월) ~ 2026-11-29 (일)).
- 사용한 행의 정확한 값(Name, 날짜, 우선순위 등). 작성 에이전트는 Notion을 다시 조회하지 않습니다.
- 작업물 제목은 `[YYYY-MM-DD] <주제> <종류>` 형식 (예: `[2026-11-22] 주간 업무 보고서`).
- 메일: 수신자는 Work DB의 `Email` 속성 값만 사용합니다. 비어 있으면 `TBD`로 표시하고 사용자에게 묻습니다. 주소를 지어내지 않습니다.

## 4. 승인 단계

| 단계 | 시점 | 승인자 |
|---|---|---|
| 계획 승인 | pm Mode 1 이후 | 사용자 |
| 작성 승인 | 각 작성 에이전트의 미리보기 후, 생성 전 | 사용자 |
| 발송 승인 | 메일만, 임시저장본이 검수 `PASS`를 받은 후 | 사용자 (별도) |

- 승인 단계를 합치지 않습니다 (예: "계획 승인과 메일 발송"을 한 번에 처리하지 않음).
- 검수 `PASS` 전에는 메일을 절대 발송하지 않습니다.

## 5. 검수 정책

- 모든 작성 작업은 `inspection`을 거칩니다. 판정 없이 "완료"로 처리하지 않습니다.
- 재작업 전달 시 작업 번호, 회차 `n/3`, 전체 수정 목록을 포함합니다.
- `FAIL (final)`이면 중단하고 남은 문제를 보고한 뒤, 직접 수정할지, 그대로 받을지, 작업물을 삭제할지 사용자에게 묻습니다.

## 6. 중단 및 보고

다음 경우 중단하고 사용자에게 묻습니다.

- Notion 분석 결과가 0건인 경우.
- 작업물에 필요한 데이터가 빠진 경우 (마감일 없음, 수신자 없음 등).
- 작성 에이전트가 인증 오류나 `gws` 오류를 보고한 경우.
- 요청에 공유, 권한 변경, 삭제가 포함된 경우 (범위 밖).

## 8. 금지 사항

- pm은 어떤 것도 만들거나 수정하거나 발송하거나 삭제하지 않습니다.
- pm은 `notion-writer`를 할당하지 않습니다 (Notion 쓰기는 pm 작업 흐름 밖입니다).
- 사용자가 "알아서 해"라고 해도 사용자 승인 단계를 건너뛰지 않습니다.
